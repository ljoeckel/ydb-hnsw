# hnsw.nim (ydb-hnsw) notes

## Concurrent writers to one index (verified 2026-10)
- Multiple processes may call `add` on the same global (see `hnsw_process_queue.nim`, `starter(n)`).
- Node ids MUST come from an atomic `$INCREMENT`: `let id = ydb_increment(ix.params.globalMeta, @["count"]) - 1`, then `ix.count = id + 1`. Never use a local `ix.count` to allocate — a stale local count collides and overwrites another process's node.
- META("count") = next free id; advanced by the increment itself (no separate metaSet).
- `VecStore.complete` is only valid for a single-writer / fresh `preloadVectors`. A detected external gap (`id > lastCount`) sets it false so `hasId` falls back to `ydb_data`.
- `cacheVector(ix, id): bool` is idempotent and grows `idToSlot` itself; also `absentIds.excl(id)` on load (an id can be reserved-but-unwritten, then appear later).
- `add` mirrors the gap `lastCount ..< id` into the cache (ids other processes reserved); own id already mirrored by `putVec`.
- `live` is now bumped atomically via `bumpLive(±1)` (`$INCREMENT` on META("live"), seeded from `ix.live` if the key is absent), and `preloadVectors` repairs a drifted value from its own count. Previously `inc ix.live; metaSet` was a lost-update race under 2+ writers, so META("live") drifted far below reality (seen: live=122901 vs count=349950, with preload loading all 349950 → `live` was the wrong number, not deletions). Track `count` = atomic truth, NODE/LEVEL subscripts = physical truth.

## In-process vector cache (`cacheVectors`) — verified 2026-10
- `cacheOn(ix)` means "caching is enabled" = `ix.params.cacheVectors`, NOT "idToSlot has entries". Keying it on the map made a **from-scratch build (fresh global, e.g. a new `--quant=int8` index) run its whole first pass with the cache silently off**; only a reopen (count>0 → preload) turned it on.
- `preloadVectors` returns early when `ix.dim <= 0 or ix.count == 0`, so an empty index leaves `ix.cache` unsized. `cacheInit(ix)` sets `ix.cache.dim = ix.dim` on first use (called from `cachePut` and `cacheVector`); without it the arena dim is 0 and everything copies to offset 0.
- `add` must call `ix.cacheInit()` (or rely on cachePut/cacheVector doing so) after `ix.dim` is settled from the first vector.
- Tests: `src/test/hnsw_cache_test.nim` covers reopen paths; fresh-build path was verified ad hoc for vqNone/vqInt8/vqInt8Fixed.

## Profiling / performance (2026-10)
- **`nim.cfg` active line has `--profiler:on --stackTrace:on --lineTrace:on`** → every run (incl. `hnsw_process_queue --processor`) is instrumented, ~**2.8× slower** (measured 5.03 vs 1.77 ms/insert at n=12k, dim384/M16/efC200). Disable for real builds.
- That instrumentation *distorts* the nimprof profile: it inflates call-heavy chains (`containsOrIncl`→`hash`→`hashWangYi1`→`rawGet`→`nextTry`, heapqueue ops) far more than flat/inlined SIMD code, so the profile's ~25% "visited set" is really ~7% unprofiled.
- `searchLayer` now uses `visitedStamp: seq[int32]` + `visitEpoch` with `seenOrMark` (epoch-stamped array) instead of `HashSet[int]`; out-of-range ids (another process's) go to a linear-scan `over: seq[int]`. Unprofiled: 1.92 → 1.77 ms/insert at n=12k.
- Insert is CPU-bound in `searchLayer` (distance + heaps + links), not YottaDB. Biggest lever remains `efConstruction` (200 → 64/100) and `M`.

## lj.nim search profile (instrumented, 2026-10)
- 98k-node vqNone index, 490k `searchBlob` queries, efSearch 64. `searchLayer` = 98.7% of samples. Leaf self-time: `simdDotF32` 24.5%, `loadVec` 11.8%, `searchLayer` 11%, distance wrapper (`isMissing` 4.9% + `dimOf` 3.2% + `dotStored`/`distanceStored`) ~11%, heap (`push`/`pop`/`sift*`/`[]`/`len`) ~15% cumulative, `getLinks` + `unpackLinks` + string `$` ~7%, `seenOrMark` 2.6%. Order of `M*2^L` ~100 expansions -> ~2-3k distances per query.
- Same profiler caveat: call-heavy frames inflated, flat SIMD under-weighted -> unprofiled the dot likely dominates (the vector cache already removed the DB reads).
- Ranked fixes: (1) build the index in an int8 mode (kernel 78 -> 57 ns, 4x fewer bytes copied); (2) zero-copy `loadVec` from `cache.floats` (it does `newSeqUninit` + `copyMem` per candidate today); (3) pick the distance kernel once per `searchStored`, not per candidate; (4) mirror `^...LINKS` as well (~12 MB here) so the walk is pure memory; (5) custom inline heap + local result count; (6) hoist the `$level` subscript and make `unpackLinks` an iterator.
- **Zero-copy `loadVec` DONE (2026-10)**: added `VecView` (borrowed ptr+len+scale, never owns) with `viewOf` / `cacheViewAt` / `distanceAt`; `dot` now takes `openArray[float32]` (as `dotInt8` already did) so a view needs no copy; `dotView`/`distanceView` are now the ONLY distance implementation and `dotStored`/`distanceStored` are thin view-based wrappers (so no second notion of distance). `searchLayer` borrows the query once and reads cached candidates in place; the YDB fallback is still `loadVec` via `distanceAt`. `dimOf` deleted (dead). Lifetime rule: a view may only outlive its seq, and for the arena only while `setLen` is not called - true for a whole search, since a search writes no vectors.
- **Measured A/B, same session** (98k-node vqNone `^HNSWArticles`, efSearch 64, identical preload time so same machine state): instrumented 3036.9 -> 2478.5 us/query (1.23x); `--profiler:off` 1855.7 -> 1622.2 us/query (1.14x, i.e. ~13% less). Recall@10 (0.952/0.972/0.992/0.996/1.000) and self-hit 25/25 unchanged; `hnsw_cache_test` / `hnsw_delete_test` / `hnsw_recall_check` all pass. NOTE the machine is currently ~3x slower than when `src/examples/profile_results.txt` was recorded (1052 us/query), so only same-session A/B numbers are meaningful.


## In-process link mirror (`cacheLinks`) — 2026-10
- `HnswParams.cacheLinks` (default true, NOT in META, honoured on every open) mirrors `^...LINKS` in `LinkStore`: dense table keyed `id * stride + level` -> `lens` (-1 unknown / 0 empty / n) plus `caps`, `offset` and `arena: seq[int]`. Capacity `2M` per entry so a list that grows while the node is linked in never has to move. `stride` re-indexes only when a node appears on a layer above all seen (log n times).
- Filled **on demand, not preloaded**, deliberately: `^...LINKS` has no node where the list is empty, so "not mirrored" and "no links" are indistinguishable in the database; a lazy fill (miss -> one read, then remember it, empty or not) is what stops a second writer's nodes from reading as empty. No `complete` flag, no O(count) cost on open (~a hundred reads per query, shared by later ones).
- Coherence: `putLinks` -> `linksStore`; `unlink`'s delete -> `linksForget`; `delete` -> `linksForgetAll`; `recordLinkFmt` resets the store (its blobs were just reinterpreted). `refreshLinks*` drops the mirror (recovery when another process relinked); a process that writes `^...LINKS` itself wants `cacheLinks = false`.
- `searchLayer` reads through `linksAt(id, level, spare) -> (ptr, n)`, borrowed like `VecView`; `getLinks` is now a copying wrapper over it for the mutating paths (`connect`, `unlink`).
- **Verified on the real 253k-node index (2026-10)**: a throwaway harness opened `^HNSWArticles` twice (cacheLinks on and off) and compared `searchBlob(k=10, ef=64)` over 1270 probes — **0 differing, ids and distances bit-identical** — then timed a warm second pass: 1544.3 vs 1927.8 us/query = **1.25x**. The mirror is answer-preserving, so the recall check's lower numbers on that run (0.952/0.960/0.980/0.988/0.996; self-hit ef=256 24/25 but exhaustive 25/25) are a property of the *bigger* graph, not a regression: the index had grown 98048 -> 253824 while the work was in progress, so those numbers are not comparable with the earlier 98k ones.
- CAVEAT found by `hnsw_delete_test`: it hand-writes and `ydb_delete`s `^...LINKS` to strand nodes, so with the mirror on `repair` answered from the stale copy (node 21 reported 0 links after repair instead of 5). Fixed by `cacheLinks = false` there — the honest config for a process that expects foreign writes. `hnsw_cache_test` now covers the mirror (incl. `refreshLinks` after a raw uint32 write) and compares a mirrored reader against a fully plain one on ef=160 walks.
- **Mode specialisation DONE (2026-10)**: added `dotCacheF32` / `dotCacheI8` (inlined kernels on raw ptr+len; `dot`/`dotInt8` are still the only implementations), routed `dotView`/`distanceView` through them, and `{.inline.}`ed both. `distanceAt` (the walk's per-candidate path) no longer builds a `VecView` or switches on `quant`: **`q`'s form IS the index's mode**, so the arena is read straight through one loop-invariant `if q.codes != nil` (the int8 branch picks `cache.scales[slot]` for vqInt8, `params.quantScale` for vqInt8Fixed). `cacheViewAt` deleted (folded into `distanceAt`); `dotView` keeps its full checks for `callers` that hand it arbitrary vectors.
- **A/B, same session, same frozen index** (stash just the change, build, run, pop, build, run): vqNone walk on 253k article index, 1270 probes k=10 ef=64, 4 runs each - before mean 1518.8, after mean 1458.9 us/query = **~1.04x (4%)**, ranges essentially non-overlapping (one after-run outlier at 1481). Answers **bit-identical**: 12700 dumped `id:dist` lines on the article index and a 400-node x 3-mode scratch dump both `diff` clean, so vqNone, vqInt8 and vqInt8Fixed are all preserved.
- `src/test/hnsw_quant_test.nim` did not compile at all before this (stale `global.nodeGlobal` / `keyGlobal` / `metaGlobal`, renamed to `globalNode` / `globalKey` / `globalMeta`); fixed `resetIndex` to derive `global & "NODE"` etc. like the sibling tests. It still samples 0 vectors from `^HNSWArticlesNODE`, so its index sections stay skipped - separate pre-existing issue, not chased.
- **Flat heap DONE (2026-10)**: `heapqueue` (a `seq[T]` of 12-byte tuples, so a 16-byte stride between comparisons, plus a `len` call with `results.len >= ef` sitting inside the inner loop) replaced by `HnswHeap`: two parallel arrays (`dists: seq[float32]`, `ids: seq[int]`) and a plain `int n`, with the one-pass sift (move parents into the hole rather than swapping per level). ONE implementation, a min-heap: `candidates` pushes `dist`, `results` pushes `-dist` so its top is the farthest (`worst` is the only place that convention shows). `AscItem`/`DescItem` and their `<` procs deleted, `heapqueue` dropped from the import. Interleaved A/B (3 runs per side, same frozen 253k index): 1473.9 -> 1293.2 us/query = **1.140x**.
- **Verification caveat from that A/B**: the heap layout decides the order among **exactly equal distances**, so the dumps are *not* byte-identical even though nothing is wrong - 0/1270 probes changed their distance profile, 1011 were identical, 202 reordered among ties, 57 return a different but equidistant id; the 3-mode scratch dump was 1194/1200 identical with 0 swaps. So check walk changes with a per-probe *distance-profile* comparison (`/tmp/check_ties.py` style), not `diff` - tie order is unspecified in HNSW. Breaking ties on `(dist, id)` would make the walk deterministic (and future diffs meaningful) at the cost of one extra compare per sift step; not taken.

## Milestone — search cost vs index size (2026-10)
- Full `lj.nim` sweep of a **742,800-node** `^HNSWArticles` (vqNone, dim 384, k=5, efSearch 64), every node used as its own query: **~503 us/query, 5.0 hits/query, 0 self-misses** (3,714,000 hits / 742,800 queries). Index tripled (253,824 -> 742,800) while per-query time stayed flat, i.e. the walk is behaving as log n, not n.
- The running average was still *declining* through the run (519.6 at cnt 642k -> 502.96 at 742.8k), because the link mirror fills lazily: the first pass over the graph pays the `^...LINKS` reads and remembers them, so a second sweep is faster than the printed average. The printed 503 is therefore an upper bound, not the steady state.
- Remaining fixed cost is now `preloadVectors`: one `ydb_get` per id on open, ~8.8 us/entry on this box, so ~6.5 s at 742,800 ids - linear in count, independent of the query path. Next levers, if wanted: an int8 index (4x fewer bytes copied; the `--quant` flag and kernels already exist) and a cheaper bulk preload than id-by-id `ydb_get`.

## linksGrow regression — build was O(n^2) (found and fixed 2026-10)
- The `cacheLinks` mirror shipped with `linksGrow` growing `ids` to *one more row* and then **unconditionally** allocating three fresh `newSeq`s and copying the whole `ids * stride` table. Its doc comment claimed "`ids` only ever rises (a `setLen`, no re-index)" — it described a draft that was never written, and the real `id + 1` growth meant a *build* (a fresh id per `add` -> `connect` -> `putLinks` -> `linksStore` -> `linksGrow`) rebuilt the table on every insert: O(n^2), with most of the cost in the allocator/page faults rather than the copy. Search never showed it because a query fills large id ranges at once.
- Symptom: `hnsw_process_queue --processor` far slower than before the mirror landed; profile `linksGrow` 91.5% of the build with `newSeq` 44% *inside* it.
- Reproduced with a throwaway `add`-only scratch build (dim 64, M8, efC64): **1559 us/insert at 10k nodes, 4804 us at 40k** — 4x the nodes for 3.1x the cost per insert.
- Fix: geometric growth of both dimensions in `linksGrow`. Only a `stride` change re-indexes (it moves every entry, since the row length is part of each index; it happens log n times as a node appears above every layer so far). A longer table is a plain `setLen` + initialising just the new tail to `lens = -1` / `offset = -1`, because row-major with a fixed stride means no existing entry moves. `ids` is now a *capacity*, not a high-water mark — every reader (`linksKnown`, `linksForget`, `linksForgetAll`) only uses it as a bound and treats `lens == -1` as unknown, so that stays correct.
- After: 553 us/insert at 10k, 671 us at 40k (2.8x / 7.2x faster; the shape is fixed — 4x nodes now costs 1.21x per insert). Build dumps (400 queries + `levelsSummary`) **byte-identical** at both sizes, i.e. layout-only. `hnsw_cache_test` and `hnsw_delete_test` unchanged; on the real 249,344-node `^HNSWArticles` (maxLevel 5) a mirror reader vs a plain reader over 400 `searchBlob` probes: **0 mismatches**, bit-identical distances.
- Workaround for a one-shot writer process, if ever needed again: `cacheLinks = false` (the mirror buys nothing in a process that builds and exits, and it cannot see another process's relinks anyway).

## Insert scaling (measured 2026-10)
- `add` is **O(log n) per vector, not O(n)**. Benchmark (dim 384, M16, efC200, cache on): 0.40 ms/insert at n=1k → 1.92 ms at n=12k (single writer); two concurrent writers 0.68 → 1.86 ms each. Increments shrink → log curve. Cache arena growth is amortized O(1) (Nim `setLen` grows cap ×2 to 32767 then ×1.5).
- Genuinely O(count) work (count = id high-water mark, never shrinks):
  - `preloadVectors` on every open: `for id in 0..<count` → one `ydb_get` each (349,950 reads on the article index for 122,901 live vectors).
  - `add`'s cache catch-up loop `for i in lastCount ..< id` — length = ids other processes took since this process's last add (~1 when balanced).
  - `delete` → `electEntry` / `relink`→`firstLiveAtLevel`, and `repair` → scan `0..<count`.
- Per-insert growth can also come from: DB outgrowing YottaDB global buffers (`getLinks` reads hit disk), or a degraded graph making `searchLayer` visit ≫ `efConstruction` nodes.
- Advisory + hierarchical: `LOCK ^G(x)` blocks only a conflicting `LOCK`; it never blocks `SET`/`KILL`/`GET`, and it protects ancestors (`^G`) but NOT descendants (`^G(x,"field")`).
- **Timeout is capped at ~2.1 s**: `YDB_LOCK_TIMEOUT = 0x7fffffff-4` is used as *nanoseconds*; the DSL `getTimeout` rejects larger values and maps 0 back to the default, so you cannot ask for an infinite wait. `ydb_lock` raises `YdbError` on timeout.
- Therefore do NOT use a lock inside a tight scan loop (a long scan into already-claimed items → the other process dies with `YDB_LOCK_TIMEOUT`).
- Claim queue items lock-free with an atomic `$INCREMENT`: `if 1 == Increment @q(idx,"work")` — exactly one racer sees 0->1. Only claim when the payload is complete (check the last-written field, e.g. "vec").
- `^HNSWArticlesQUEUE` (`gbl & "QUEUE"`) holds WorkItems keyed by a single string subscript `idxref` = "articleId,chunk"; fields idxref/title/vec written via `saveObject[WorkItem](idxref, …, globalName="^HNSWArticlesQUEUE")`.
- M utility: `mumps -run %XCMD '...'`; `F k="" …` runs ONCE (value-list FOR) — use `F  S k=$O(g(k)) Q:k="" …` for an unbounded loop, and init `S k=""` first.
- Running the processor needs the venv: `source hnsw_env/bin/activate` (else Python numpy import fails).
